# Transformer LMs on the Snapdragon 8+ Gen 1 (Hexagon V69): CPU, HTP (QNN), tinygrad HVX

Encoder-only and decoder-only language models on the Xiaomi 12S (SM8475), each run three ways:

- **CPU**: ONNX Runtime 1.26 on the phone's CPU, 4 threads, fp32 and ORT dynamic int8.
- **HTP**: the same static ONNX graphs through the QNN EP (strict, no CPU fallback, EP-context cache,
  `htp_performance_mode=burst`), fp16 or onnxsim whole-graph QDQ (`onnxsim.full_qdq`).
- **tinygrad HVX**: the matmul-heavy kernels generated by our tinygrad HVX codegen
  (`onnxsim/tinygrad`, stage 1 int / stage 2 qfloat) and run on the DSP through our own FastRPC skel.

All phone numbers are medians taken under the shared phone lock (`~/.cache/android-phone/phone-run`),
from `/data/local/tmp/codex-android-llm-tinygrad/`.

## Encoder: MiniLM-L6 (all-MiniLM-L6-v2), sequence 128

22.7M parameters (6 layers, hidden 384, 12 heads, FFN 1536). The graph includes sentence-transformers'
mean pooling and L2 normalization, so its output is the sentence embedding. Accuracy is the cosine
between the phone's embedding and fp32 torch's over 20 fixed sentences (`models.SENTENCES`).

| path | ms / inference | embedding cos vs fp32 (mean / min) | phone peak RSS |
|---|---:|---|---:|
| CPU fp32, 4 threads | 24.7 | 1.000000 / 1.000000 | 186 MB |
| CPU ORT dynamic int8, 4 threads | 11.1 | 0.965 / 0.948 | 90 MB |
| **HTP fp16** (fp32 graph, QNN runs it in fp16) | **1.94** | **0.999998 / 0.999997** | 446 MB* |
| HTP W8A16 (onnxsim QDQ, uint16 activations; LayerNorm/Softmax/GELU fp16) | 3.34 | 0.99905 / 0.99872 | 351 MB* |
| HTP W8A8 (same, uint8 activations) | 2.54 | 0.867 / 0.820 | 283 MB* |
| HTP int8 Linear only (Gemm/MatMul uint8, rest fp16) | 2.33 | 0.953 / 0.924 | 372 MB* |

\* peak RSS of the process that also compiled the EP-context cache on first use.

- **fp16 on the HTP wins outright.** It is 12.7x faster than the CPU in fp32 and 5.7x faster than
  CPU int8, and it is as accurate as fp32. At seq 128 the model is about 1.4 GMAC, which the HTP's
  fp16 path covers comfortably.
- **int8 doesn't pay here.** Every int8 variant is *slower* than fp16. The float islands that int8
  needs (LayerNorm, Softmax, GELU, the additive mask) cost more in conversions than int8 saves on a
  model this small. The variants that are accurate (W8A16) are the slowest.
- **W8A8 loses accuracy through activation outliers,** a known BERT property. The FFN outputs and
  residual stream have a few huge channels, so one uint8 scale per tensor flattens everything else.
  The same happens to ORT's dynamic int8 on the CPU (0.965).
- **The attention mask needed a fix before any quantization worked.** HF's additive mask is
  `(1 - mask) * finfo(fp32).min = -3.4e38`: that is -inf in fp16, and a range that crushes every
  score it shares a quantization scale with. `export_minilm.py` rewrites it to -1e4 (exp(-1e4) = 0,
  so the masking is identical), and `quantize_minilm.py` keeps the mask path and the score Adds it
  feeds in fp16. Before the fix, W8A16 was at cos 0.0.

## Decoder: SmolLM2-135M (Llama, 30 layers, hidden 576, GQA 9/3 heads), prefill 128, KV cache 256

A plain-PyTorch Llama (`export_smollm.py`; prefill logits within 1.8e-5 of transformers, and greedy
decoding identical to `transformers.generate` for 32 tokens) exported as two static graphs: a
128-token prefill and a one-token decode step with the KV cache as graph I/O (the host writes each
step's new K/V row). Accuracy is measured two ways over 10 fixed prompts (`models.PROMPTS`), 32
tokens each: **free-running** (leading tokens identical to fp32 greedy) and **teacher-forced** (fp32's
tokens fed back; per-step top-1 agreement and logits cosine).

| path | prefill 128 tok | decode tok/s | free: all 32 tokens identical | forced top-1 / logits cos min | phone peak RSS |
|---|---:|---:|---|---|---:|
| CPU fp32, 4 threads | 258 ms | 41 | 10/10 prompts | 1.000 / 1.000 | 1.39 GB |
| CPU ORT dynamic int8 (per-channel), 4 threads | 92 ms | 73 | 0/10 (diverge after 0-12 tokens) | 0.897 / 0.71 | 453 MB |
| HTP fp16 (fp16 weights, activations, KV cache, logits) | 25.4 ms | 110 | 0/10 | 0.722 / **-0.28** | 2.3 GB* |

\* includes compiling both EP-context caches in the same process (~21 s, once).

- **The HTP is 10x faster than the CPU at prefill and 2.7x at decode,** but its fp16 run is
  **not accurate yet**: the prefill logits are right for some prompts (cos 0.995) and wrong for
  others (cos -0.06), and the decode steps are erratic. The same fp16 graph on host ORT is
  accurate (32/32 tokens identical on every prompt, logits cos >= 0.999996), so this is how the HTP
  executes it, not fp16 itself. **Open, not yet bisected.** Suspects: the -1e4 additive masks in
  fp16 softmax, the rotary `index_select` on `pos`, and QNN's accumulation precision in the
  576-wide RMSNorm reductions. `bisect_precision.py` in `../vision_models/bevformer_tiny/` is the tool.
- **CPU dynamic int8 is not usable for this model** even per-channel: dynamic per-tensor activation
  quantization breaks on the Llama residual stream's outlier channels (logits cos down to 0.71).
- **Decode is memory-bound.** A decode step reads every weight once: 135M params = 270 MB in fp16,
  135 MB in int8. At 110 tok/s the HTP streams ~30 GB/s of fp16 weights, near this SoC's practical
  LPDDR5 bandwidth, so int8 or int4 weights (the next step) are what would raise decode tok/s, not
  more compute.

## tinygrad HVX: the decode-step GEMVs on the DSP

Decode is one W8A8 GEMV per Linear: a uint8 activation row [1,K] times int8 weights [K,N], int32
accumulation. That is exactly Hexagon's `vrmpybusv` (u8 x s8 dot4 -> s32). `hvx/llm_kernels.py`
writes SmolLM2's GEMV shapes as plain tinygrad Tensor code, generates them with our HVX codegen
(`onnxsim/tinygrad` `hvx-vrmpy-mixed` 9aa4f66a1 = stage 1 + stage 2 + the vrmpy GEMV fix, onnxsim/tinygrad#5), and
checks them bit-exact against numpy under qemu (`MOCKDSP=1`). `hvx/build.sh` runs them on the phone's CDSP
through our own FastRPC skel (rpcmem buffers, DSP-side timing, one QuRT thread holding the HVX unit), next to
a hand-written vrmpy GEMV as the reference. All outputs bit-exact on the phone. Medians of 21 runs, one DSP
thread, under the phone lock:

| kernel | up 576x1536 (gate/up) | down 1536x576 | q/o 576x576 | k/v 576x192 | weight stream |
|---|---:|---:|---:|---:|---:|
| tinygrad at 847af7eab (before the fix), turbo | 2.30 ms | 9.09 ms | | | 0.10-0.38 GB/s |
| tinygrad now, row-major `x.matmul(W, dtype=int32)`, turbo | 6.14 ms | 6.02 ms | | | 0.14 GB/s |
| **tinygrad now, prepacked weights, turbo** | **95 us** | **94 us** | **35 us** | **12 us** | **9.2-9.5 GB/s** |
| hand vrmpy GEMV (prepacked), turbo | 43 us | 42 us | 15 us | 5 us | 20.6-22.1 GB/s |
| tinygrad now, prepacked, default clocks | 178 us | 179 us | 66 us | 22 us | 4.9-5.0 GB/s |
| hand vrmpy, default clocks | 82 us | 85 us | 29 us | 10 us | 10.4-11.4 GB/s |

"Prepacked" is the hand kernel's weight layout, `Wp[N/32][K/4][32][4]`: one 128-byte vector per 32 outputs x 4 K.
In tinygrad it is the same GEMV written over that layout, `(x.reshape(1,K/4,1,4) * Wp).sum((1,3), dtype=int32)`
with `TC_OPT=1` (two reduce axes); the weights are packed once on the host (`llm_kernels.py pack()`).

What was wrong and what the fix changed (onnxsim/tinygrad#5):

- **The vrmpy TensorCore never matched a GEMV.** Two reasons, both verified: the TC required both MUL inputs to
  have the same dtype, and dtype promotion turns u8 x s8 into `short(u8) * short(s8)`, for which the DSP TC list had
  no entry; and with M=1 the activation side has no range of its own, so every TC axis choice was skipped. The fix
  adds a (uint8, int8) TC entry (rendered as `vrmpybusv` with the 4 activation bytes splat), looks through
  value-preserving widening casts, and lets a TC with M=1 match without an M range.
- **Once matched, it was slower than scalar code** (row-major above: 6 ms): the 32-lane int32 accumulator round-tripped
  through 32 scalar register-array loads/stores per vrmpy, and the weight vector was rebuilt from 32-byte pieces with
  `vinsert` chains. tinygrad now coalesces DSP register arrays (the accumulator is one HVX register), caps DSP loads
  in bytes rather than lanes (a vrmpy's 128 weight bytes are one `vmem`), and does no extra M/N upcast inside the
  vrmpy's 32 lanes. The prepacked GEMV's inner loop is now one `vmem`, one `vsplat` and one `vrmpy` per 128 weight
  bytes.
- **Row-major weights stay slow** (the TC's B operand is 4 rows' bytes interleaved, gathered bytewise): prepack.
- **Remaining 2.2x to the hand kernel:** a loop-carried lane permutation (`vdeal`+`vshuff`) between the register
  accumulator's lane order and the WMMA's, plus a single accumulator chain (the hand kernel keeps 4 independent
  accumulators). Fixing the permutation needs the TC's upcast-axis order to match the accumulator's layout in the
  generic expander.
- **Buffers need slack:** HVX unaligned loads (`vmemu`) touch the whole 128-byte lines they span; the client pads
  every rpcmem buffer by 256 bytes (an exactly-sized weight buffer faulted with a TLB miss past its end).
- **Stack:** the kernels run on a QuRT thread with a 256 KB stack; on the FastRPC thread tinygrad's kernels crashed.

**Projected full-model decode** (GEMVs only, one DSP thread, turbo; projections from the per-kernel times, not
measured end to end). One SmolLM2 token reads 106 MB of int8 layer weights (30 x q, k, v, o, gate, up, down) + 28 MB
of int8 LM head = 134.5 MB:

| path | GEMV time / token | tok/s |
|---|---:|---:|
| tinygrad at 847af7eab (0.38 GB/s) | ~354 ms | ~3 |
| **tinygrad now, prepacked (30 x 378 us + head at 9.4 GB/s)** | **~14.3 ms** | **~70 (projected)** |
| hand vrmpy, one thread (30 x 168 us + head at 21 GB/s) | ~6.4 ms | ~155 (projected) |
| hand vrmpy, 4 HVX threads (bandwidth-bound at ~40-50 GB/s LPDDR5, estimate) | ~3 ms | ~300 (projected) |
| measured HTP fp16 (270 MB fp16 weights) | 9.0 ms / step | 110 (measured, accuracy open) |

Other tinygrad limits, unchanged: no threading (stage 3: one of the 4 HVX contexts; decode is bandwidth-bound, so
threads help until DDR saturates, ~2x estimate); no HMX (only reachable through QNN; matters for compute-bound
prefill, not decode); scalar exp/sigmoid on V69 (SiLU/softmax are a few thousand elements per layer at batch 1,
well under 1 ms per token even scalar).

## Files

| file | what |
|---|---|
| `models.py` | pinned Hub revisions + sha256 of the weights; the evaluation sentences and prompts |
| `export_minilm.py` | MiniLM-L6 -> static ONNX (int32 ids, bounded mask, pooling in-graph), fp32 references, phone inputs |
| `quantize_minilm.py` | CPU dynamic int8 and the onnxsim QDQ variants for the HTP |
| `eval_encoder.py` | embedding cosine vs fp32 (phone outputs or host ORT) |

| `export_smollm.py` | SmolLM2-135M -> prefill + KV-cache step graphs (fp32, or `--fp16-only`), fp32 greedy references |
| `quantize_smollm.py` | CPU dynamic int8 (per-channel) and onnxsim W8A16 QDQ variants |
| `eval_decoder.py` | free-running and teacher-forced agreement vs fp32 (phone outputs or host ORT) |
| `hvx/llm_kernels.py` | the decode GEMVs as plain tinygrad Tensor code (row-major and prepacked) -> kernels.h, exact under qemu |
| `hvx/llm_impl.c`, `llm_rpc.idl`, `llm_client.c`, `build.sh` | FastRPC skel + client timing the tinygrad and hand vrmpy GEMVs on the CDSP |
| `run_phone.sh` | build `llm_run`, push libs/models/inputs (by md5), run, pull outputs |

## Reproduce

Each heavy step under `systemd-run --user --wait --collect --pipe -p MemoryMax=12G -p MemorySwapMax=0`;
every phone step under `~/.cache/android-phone/phone-run`. `W=~/.cache/llm-work`, and the onnxsim
checkout on `PYTHONPATH`.

```
python export_minilm.py --work $W
python quantize_minilm.py --work $W
ORT_THREADS=4 ./run_phone.sh enc $W/enc.fp32.onnx cpu 22 $W/enc_in 20 $W/ph_enc_cpu_fp32
QNN_PERF=burst ./run_phone.sh enc $W/enc.fp32.onnx htp 22 $W/enc_in 20 $W/ph_enc_htp_fp32
python eval_encoder.py --work $W --phone $W/ph_enc_htp_fp32
```

tinygrad HVX kernels (`onnxsim/tinygrad` branch `hvx-vrmpy-mixed`, 9aa4f66a1; Hexagon SDK 6.4 on the host;
`D` is the phone directory):

```
PYTHONPATH=<tinygrad checkout> CC=clang-19 HVX_ARCH=v69 python hvx/llm_kernels.py --out $W/hvx
TURBO=1 D=/data/local/tmp/<yours>/hvx HEXAGON_SDK_ROOT=... HEXAGON_TOOLCHAIN=.../Tools DATA=$W/hvx hvx/build.sh
```

The ORT/QNN libraries come from `../htp_exploration/qnn_shell/fetch_libs.sh` (Maven Central, not
committed).
