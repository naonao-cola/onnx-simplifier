# EXL3 / QTIP trellis quantization: survey and decision

**Status: not ported.** This is a research note, not documentation of a
shipped feature -- it records why [EXL3](https://github.com/turboderp-org/exllamav3)
(and the QTIP algorithm it streamlines) was surveyed and rejected as a
candidate for onnxsim's quantization series (AdaRound, AWQ, GPTQ, HQQ,
AutoRound, NF4, SmoothQuant, LLM.int8(), SqueezeLLM, LoRC, QuIP#, OmniQuant,
AQLM), so the question doesn't get re-litigated from scratch later.

## What EXL3 actually is

[`doc/exl3.md`](https://github.com/turboderp-org/exllamav3/blob/master/doc/exl3.md)
in the exllamav3 repo is short by design: it describes EXL3 as a variant of
**QTIP** ("Quantization with Trellises and Incoherence Processing," Tseng et
al., Cornell RelaxML, [NeurIPS 2024](https://arxiv.org/abs/2406.11235)) that
"deviates from QTIP in how tensors are regularized and packed," and
explicitly defers the full format description to the source and CUDA
kernels. The doc itself doesn't restate QTIP's math, so this note goes to
the paper's own mechanism to evaluate portability.

The headline claim holds up: EXL3 is reported competitive with or ahead of
GGUF-family quantizations at matched bitrate across Llama and Mistral
models, and -- notably for a trellis method -- supports fractional
bits-per-weight rather than being locked to block-INT4-style granularity.

## How QTIP quantizes a weight matrix

Three stages, the last one genuinely sequential:

1. **Incoherence processing.** Random Hadamard rotations applied to the
   weight matrix push its distribution toward i.i.d. Gaussian, smoothing
   outliers before quantization. Same lineage as QuIP#'s rotation step, which
   onnxsim already ports in `apply_quip_sharp`.
2. **Trellis-coded encoding (Viterbi search).** Instead of a
   vector-quantization codebook -- exponential in dimension, which is why
   AQLM/QuIP# cap out around dimension 8 -- QTIP finds the error-minimizing
   path through a "bitshift trellis" via Viterbi search, decoupling codebook
   size from both bitrate and effective dimension. This part runs once,
   offline, at quantize time.
3. **Bitshift-trellis decode ("computed codes").** Reconstruction is a
   *stateful walk*: each output element's code depends on a sliding window of
   the previous state's bits, and the code itself is produced by a
   pseudorandom Gaussian hash function computed on the fly rather than looked
   up in a stored table -- trading memory for compute so the trellis never
   needs to be materialized.

## Why it breaks onnxsim's porting pattern

Every quantization scheme onnxsim has ported -- including the other
codebook-based ones -- reduces at inference time to elementwise, stateless
ONNX ops: a block's dequantized value depends only on its own stored code,
never on a neighbor's. EXL3's stage 3 is the opposite by construction: it's a
state machine, and the state itself is defined by consecutive elements.

| Technique | Codebook structure | Decode dependency | ONNX decode |
|---|---|---|---|
| NF4 | one fixed global codebook | none -- per-element | `Gather` |
| SqueezeLLM | one codebook, fit per group | none -- per-group | `GatherND` |
| AQLM | M codebooks, summed additively | none -- M parallel lookups | `Gather` x M + `Add` |
| QuIP# | fixed E8 lattice, nearest-point decode | none -- per-vector | arithmetic, no table |
| **EXL3 / QTIP** | procedural, generated by trellis state | **sequential -- state carries forward** | `Loop`/`Scan` + hash fn |

Reproducing stage 3 faithfully would need an ONNX `Loop`/`Scan` construct
carrying bit-shift state across a whole row, plus an exact reimplementation
of QTIP's pseudorandom Gaussian hash -- precise bit-level behavior that's
only meaningfully checkable against the reference CUDA kernel, not derivable
independently the way SmoothQuant's scale formula or AQLM's residual k-means
were.

## Decision

**Skip -- do not port EXL3/QTIP to onnxsim.**

Stage 1 (incoherence processing) isn't a new idea worth a standalone module
-- onnxsim already has it via `apply_quip_sharp`'s rotation. The part of QTIP
that's actually novel, the bitshift-trellis decode, is inherently sequential
and depends on a bespoke computed-hash function, which breaks the pattern
that has made every prior port here tractable: reduce the paper's own solver
to a classical, independently verifiable technique, but keep the *decode
graph* itself a stateless composition of standard ONNX ops. EXL3's core
mechanism resists that substitution -- the sequential state machine *is* the
technique, not an implementation detail standing in for something simpler.
